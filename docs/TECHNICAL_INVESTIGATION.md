# Full Investigation Report: Antigravity IDE `v2.6.0` Battery, Performance & Token Economics

## 1. Plain-English Overview

During real-world use on an Apple M1 MacBook Air (`MacBookAir10,1`, fanless passive cooling, 8 GB RAM), Antigravity IDE `v2.6.0` caused severe chassis heat (`40.6 °C`), `~13.93 W` continuous power draw even while idle (5x–8x normal idle draw), and stalled charging.

Investigation across macOS battery telemetry (`AppleSmartBattery`), process sampling (`sample`), open file handles (`lsof`), extension manifests, and binary disassembly uncovered **four compounding issues**:

1. **Issue A — Infinite 100%–300% CPU File-Copy Loop:** When Antigravity's external `agy --hub` agent shortens a workspace file on disk at the exact moment VS Code's default **Local History** (`WorkingCopyHistoryService`) is copying that file to `User/History/`, Electron `39.2.3`'s `libuv` file-copy worker hits end-of-file early (`0` bytes read), misses its loop exit check, and spins that CPU core at **100% forever** until a full `Cmd+Q` app exit.
2. **Issue B — 25% `libuv` Worker Pool Starvation at Launch:** `@vscode/policy-watcher` permanently blocks 1 of Node's default 4 `libuv` worker threads on a semaphore at startup, leaving only 3 workers for all main-process file I/O.
3. **Issue C — Non-Occluded Background GPU, 15s Health Pings & 8 GB RAM Swap:** Disabled window occlusion + 15-second `/healthz` probes + 3 GB default TS Server cap + uncapped editor tabs push 8–16 GB Apple Silicon Macs into constant GPU wakeups and SSD swap compression.
4. **Issue D — Always-On Plugin Prompt-Token Overhead:** Every enabled plugin injects all of its skill descriptions into every single chat step (`~8,600+` baseline tokens per step across 6 plugins, with `science`'s 48 skills accounting for `~5,410` tokens/step on its own), compounded by unfiltered workspace searches scanning lockfiles and minified bundles.

## 2. Investigatory Findings on Plugin Toggling & AI Token Economics

Auditing Antigravity's Language Server (`GetAllPlugins`) and `~/.gemini/config/plugins/` revealed a major economic & latency win that most users never see:

| Installed Plugin | Bundled Skills | Extra Always-On Components | Est. Baseline Prompt Cost (Every Step) |
| :--- | :--- | :--- | :--- |
| **`science`** | 48 | 1 MCP server + 1 global rule (`AGENTS.md`) | **~5,410 tokens / step** (`21,644` chars — **63% of total**) |
| **`firebase`** | 13 | 1 subagent (`firestore-rules-author`) | **~1,575 tokens / step** (`6,300` chars) |
| **`chrome-devtools-plugin`** | 6 | — | **~625 tokens / step** (`2,508` chars) |
| **`modern-web-guidance-plugin`** | 2 | — | **~500 tokens / step** (`1,997` chars) |
| **`android-cli-plugin`** | 3 | Sidecar skills | **~390 tokens / step** (`1,558` chars) |
| **`google-antigravity-sdk`** | 1 | — | **~90 tokens / step** (`363` chars) |

- **Why this matters economically:** Because an autonomous coding task routinely runs **15–30 internal tool-calling steps** per user request, keeping unused domain plugins (`science`, `firebase`, `android-cli-plugin`) enabled adds **~110,000 to ~220,000 unnecessary input tokens per task** — burning quota faster and increasing time-to-first-token latency.
- **Zero-restart fix:** Toggling unused plugins off in Antigravity's **Customizations -> Plugins** page takes effect **live on the very next turn** without restarting the IDE, and pairing `search.exclude` lockfile shields with `/compact` on long threads keeps context growth lean.

## 3. Low-Level Engineering Proof (For Google Antigravity Engineers)

### 3.1 Thread Sampling & Leaked File Descriptors
- **`sample <electron_pid> 3`:** Showed 2 of 4 `libuv-worker` threads pinned (`2358 / 2358` samples) at `_uv__fs_post + 2432` (`pread` / `sendfile` / `_platform_memset`), and 1 `libuv-worker` thread parked in `PolicyWatcher::Execute` (`semaphore_wait_trap`).
- **`lsof -p <electron_pid>`:** Showed 4 open file descriptors held across 6+ days between workspace source files (`O_RDONLY`) and `~/Library/Application Support/Antigravity IDE/User/History/<hash>/<4char>.<ext>` (`O_WRONLY`), matching the 4-character snapshot filenames generated by `WorkingCopyHistoryModel.doAddEntry` in `out/vs/workbench/workbench.desktop.main.js` (`@26772671`).
- **Bundle Call-Site Audit:** Scanning all `.js` bundles under `Contents/Resources/app/out/` confirmed `WorkingCopyHistoryModel` (`workbench.localHistory.enabled`) is the **only** background feature calling `fileService.cloneFile` -> `DiskFileSystemProvider.doCloneFile` (`out/main.js` `@828235`).

### 3.2 ARM64 Disassembly of `_uv__fs_post` (`Electron Framework` v39.2.3)
Disassembling `_uv__fs_post` (`0x286cdf0`) in `Electron Framework`:

1. `0x286d570`: `uv__fs_copyfile` calls `fstat(srcfd)` once and stores `st_size` in `x23` (`bytes_to_send`).
2. `0x286d730`: Loops calling `uv__fs_sendfile(dstfd, srcfd, in_offset, bytes_to_send)`.
3. `0x286d96c`: Inside `uv__fs_sendfile`, macOS `sendfile(2)` fails with `ENOTSOCK` (`0x26`) because `dstfd` is a regular file, falling back every iteration to `uv__fs_sendfile_emul` (`0x286d9f8`: 8 KB stack `memset` at `0x286da14` + `pread` at `0x286da80`).
4. When `agy --hub` truncates/replaces the workspace file on disk after `fstat(srcfd)`, `pread()` hits EOF and returns `0` (`written = x22 = 0`) while `bytes_to_send` (`x23`) remains `> 0`.
5. Loop termination check at `0x286d77c`–`0x286d790`:
   ```armasm
   286d77c: tbnz x22, #0x3f, 0x286d794   ; ONLY breaks if written < 0 (sign bit set)!
   286d784: add  x8, x8, x22             ; in_offset += 0
   286d78c: subs x23, x23, x22           ; bytes_to_send -= 0 (never reaches 0)
   286d790: b.ne 0x286d730               ; spins at 100% CPU forever
   ```
